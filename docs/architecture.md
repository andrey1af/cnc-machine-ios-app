# Архитектура

## Модули

| Каталог | Роль |
|---|---|
| `cncapp/Models` | Контракт JSON, координаты, состояние программы и правила доступности действий |
| `cncapp/Networking` | Запросы HTTP к `cncbridge` и чтение потока SSE |
| `cncapp/ViewModels` | Связь с сервером, обновление состояния, кэш траектории и журнал |
| `cncapp/Views` | Вкладки «Пульт» и «G-code», настройки подключения, подтверждение запуска |
| `tests` | Тесты XCTest. `Package.swift` включает те же модели и правила, что проект Xcode |

## Поток данных

1. Пользователь выбирает файл через системное окно iOS. `MachineViewModel` проверяет состояние подключения, доступ к файлу и размер. `CNCAPIClient` передаёт файл серверу.
2. `cncbridge` хранит выбранную программу и сообщает её состояние через SSE. Клиент декодирует `status` и обновляет интерфейс. Один снимок состояния используется для обеих вкладок.
3. Для новой ревизии клиент запрашивает геометрию отдельно. Пока ключ сервера и ревизии совпадает, при переключении вкладок используются данные из памяти.
4. При обрыве UI сразу получает состояние «Сервер недоступен». После ранее успешной связи клиент делает до трёх попыток с паузой 5 секунд. До получения нового статуса загрузка и настройки заблокированы.

## Решение и его цена

Сервер владеет состоянием станка и выбранного файла. Клиент показывает полученные данные и запрашивает действия. Это позволяет нескольким клиентам увидеть один статус и использовать общую геометрию. Цена — зависимость от сети и задержка отображения до следующего сообщения о состоянии. Альтернатива с опросом HTTP проще в реализации, но каждому клиенту пришлось бы самостоятельно запрашивать журнал и статус с нужной частотой.

Логика доступности действий и лимит переподключений вынесены в модели, поэтому тесты могут выполнять эти правила без SwiftUI, GRBL и системных таймеров. Для проверки подключения, таймера и отображения экранов требуется запуск приложения.
